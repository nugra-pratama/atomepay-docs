AtomePay (APB) — Platform Documentation

AtomePay is Atome's Indonesia digital-wallet & pay-later backend platform. This site documents the microservices, REST APIs, Temporal workflows, provider integrations, and infrastructure under the atomepay GitHub org.

Source of truth
Code is the source of truth. All ~30 org repos are cloned locally; each service is self-contained. Endpoint lists here are an inventory to locate code, not a substitute for reading the controllers.

System architecture

APB is a set of independently deployable Spring Boot 3 microservices (Kotlin, Java 21) orchestrated with Temporal for every multi-step / external-dependent flow. PostgreSQL (JPA/Hibernate, Flyway) holds transactional state, MongoDB holds reference data, Redis holds cache/transient state, Kafka handles messaging, and Spring Cloud Config centralizes configuration.

APB system overview — gateway fronting, Temporal-orchestrated microservices, and provider adapters (Doku / GDC / Artajasa / Rintis / Atome).

  • API gateway fronts public consumer endpoints; each service is also independently reachable internally.
  • Temporal runs workflows + activities (e.g. AtomeTransferWorkflow, DokuTransferWorkflow, GdcTransferWorkflow, *RecordBookingWorkflow).
  • Provider adapters: Doku (PPOB billers, cashout, payouts), GDC Pay (bank transfer), Artajasa (QRIS, top-up), Rintis (top-up notifications), Atome (internal wallet transfer).
  • Observability: Spring Actuator + Prometheus + Logstash JSON logs.
Temporal queues
Shared queues: ACCOUNT_SERVICE_TASK_QUEUE, TOPUP_RECORD_BOOKING_TASK_QUEUE, TRANSFER_RECORD_BOOKING_TASK_QUEUE, QRIS_RECORD_BOOKING_TASK_QUEUE, PPOB_TASK_QUEUE, TRANSACTION_HISTORY_SERVICE_TASK_QUEUE.

Security model

  • Public / partner-facing API → JWT resource server (JWTAuthenticationFilter), issuer OAUTH2_JWT_ISSUER_URI.
  • Internal service-to-service → shared API key ZERO_TRUST_SERVICE_KEY via InternalApiFilter (e.g. RintisApiFilter in account-service is a variant).
  • Back-office → BackofficeApiFilter; Client token → ClientTokenAuthenticationFilter.

Transfer flows

All confirm endpoints share a shape: validate JWT/booking → start a Temporal workflow (async) → booking marked PROCESSED → respond immediately with the booking reference. A *RecordBookingWorkflow tracks the booking lifecycle; a final confirmBooking signal (in finally) completes it, otherwise the booking expires (~15 min).

Atome — internal wallet transfer (no saga)

Transfer routing (inquiry → provider)

POST /api/v1/transfers/inquiry → TransferRoutingService.determineGateway(): (1) smart rules (preferred bank-code exact match, then preferred amount threshold), (2) weighted percentage split (weights must sum to exactly 100). Forward via RequestDispatcher to /api/v1/transfers/{partner}/inquiry, then cache transfer:{bookingId} → partnerName in Redis (TTL 15 min). Config atomepay.partners.routing.transfer is @RefreshScope hot-reloadable from Config Server.

QRIS · Top-up · PPOB

  • QRIS (payment-service + account-service): Artajasa QRIS payment/refund, network sign-on/sign-off/echo/cutover; QRIS payload parsing via QrisParser in atomepay-common. Routes under /api/v1/qr, /api/v1/qr/artajasa.
  • Top-up (topup-service): Artajasa top-up + status inquiry (POST /status-inquiry); Rintis notification ingestion under /api/v1/rintis/notification.
  • PPOB (ppob-service): biller inquiry + payment via Doku; routes under /api/v1/biller/doku, orders under /api/v1/biller.

Key code — what makes the integrations work

The snippets below are the parts of the platform that are easiest to get wrong or misunderstand. Paths are relative to each service repo at /opt/atomepay/.

1 · Idempotent wallet credit — account-service TopupWalletServiceImpl.kt
The single place every top-up (Artajasa/Rintis) money-in lands. Idempotency key = partnerTransactionId; all limits are checked before the balance mutation; tx row is written before the balance so a crash never credits twice.
override fun creditTopupWallet(
    accountNumber: String,
    amount: BigDecimal,
    partnerTransactionId: String,
    referenceNumber: String
): UUID {
    // Idempotency guard — a partnerTransactionId is credited exactly once.
    // Re-delivered partner notifications become a no-op returning the same wallet.
    if (walletTransactionRepository.existsByPartnerTransactionId(partnerTransactionId)) {
        val processed = walletTransactionRepository.findByPartnerTransactionId(partnerTransactionId)
            .orElseThrow { IllegalStateException("tx exists but not found") }
        return processed.wallet?.id ?: throw IllegalStateException("no wallet id")
    }

    val wallet = walletRepository.findByAccountNumber(accountNumber)
        .orElseThrow { ErrorCode.WALLET_NOT_FOUND_EXCEPTION.toException() }

    val balanceBefore = wallet.balance
    val balanceAfter  = balanceBefore + amount

    // Wallet balance + frequency limits are enforced before mutating anything
    val limit = walletLimitService.getWalletBalanceLimits(wallet)
    if (balanceAfter < limit.minLimit || balanceAfter > limit.maxLimit)
        throw ErrorCode.TRANSACTION_EXCEED_LIMIT_AMOUNT.toException()

    walletLimitService.validateHourlyTopupCount(wallet)
    walletLimitService.validateDailyCountLimit(wallet)
    walletLimitService.validateDailyAmountLimit(wallet, amount)
    walletLimitService.validateMonthlyCreditLimit(wallet, amount)

    val tx = WalletTransaction(
        wallet = wallet,
        accountNumber = wallet.accountNumber,
        partnerTransactionId = partnerTransactionId,
        referenceNumber = referenceNumber,
        type = WalletTransactionType.CREDIT,
        currency = wallet.currency,
        amount = amount,
        balanceBefore = balanceBefore,
        balanceAfter  = balanceAfter,
    )
    walletTransactionRepository.save(tx)   // tx row first (audit trail)
    wallet.balance = balanceAfter
    walletRepository.save(wallet)          // then balance
    return wallet.id
}
2 · Artajasa inbound auth + ACK — topup-service ArtajasaService.kt
Artajasa uses a static shared-secret match (username + signature hash) instead of HMAC/HTTPS-mTLS. The response body carries a partner status-code ACK (SUCCESS / ALREADY_PAID / ILLEGAL_SIGNATURE / …) — the workflow runs synchronously within a 30s client timeout.
// Inbound partner callbacks are authenticated by matching the
// configured username + signature-hash (shared secret), not an OAuth flow.
private fun isSignatureValid(request: ArtajasaNotificationRequest): Boolean {
    return request.username == artajasaConfig.username
        && request.signature == artajasaConfig.signatureHash
}

override fun handlePaymentNotification(request: ArtajasaNotificationRequest): ArtajasaNotificationResponse {
    if (isSignatureValid(request).not()) {
        // Partner expects an ACK with a status code in the response body
        return createResponse("", request.signature,
            TransactionStatusCode.ILLEGAL_SIGNATURE_TRANSACTION)
    }

    val booking = artajasaTransactionBookingRepository.findById(request.bookingId).orElse(null)
    if (booking == null)
        return createResponse(request.bookingId, request.signature,
            TransactionStatusCode.NO_TRANSACTION_FOUND)
    // ... amount/status validation returns ALREADY_PAID / FAILED / INVALID_AMOUNT ...

    // Valid → persist order then hand off to the Temporal workflow
    val order = createTransactionOrder(request, booking)          // status RECEIVED
    return startTopupWorkflow(request, booking, order)            // sync ACK w/ result code
}
3 · Doku outbound HMAC-SHA512 — transfer-service DokuTransferSignatureServiceImpl.kt
Doku signatures are HMAC-SHA512(clientSecret) over a canonical string METHOD:URL:TOKEN:SHA256(minifiedBody):ISO_TIMESTAMP. The minified body must be the exact canonical JSON (Jackson readTree) or the hash won't match on Doku's side.
// Outbound Doku request signature: HMAC-SHA512 over
// "HTTP_METHOD:endpointUrl:accessToken:sha256(minifiedBody):timestamp"
// using the *client secret* as the HMAC key.
override fun <T> createFromPayload(
    httpMethod: String,
    endpointUrl: String,
    accessToken: String,
    payload: T,
): ByteArray {
    val requestBody    = objectMapper.writeValueAsString(payload)
    val minifiedBody   = objectMapper.readTree(requestBody).toString()  // canonical JSON
    val hashedBodyHex  = messageDigest.digest(minifiedBody.toByteArray(Charsets.UTF_8))
        .joinToString("") { "%02x".format(it) }.lowercase()

    return "${httpMethod.uppercase()}:$endpointUrl:$accessToken:$hashedBodyHex:$timestamp"
        .toByteArray(Charsets.UTF_8)
}

override fun createSignature(byteArrayToSign: ByteArray): String {
    val mac = Mac.getInstance("HmacSHA512")
    val key = SecretKeySpec(properties.clientSecret.toByteArray(Charsets.UTF_8), "HmacSHA512")
    mac.init(key)
    return Base64.getEncoder().encodeToString(mac.doFinal(byteArrayToSign))
}
4 · Doku webhook verification — transfer-service DokuNotificationService.kt
Inbound Doku webhooks (unpaid / refund) are verified with a symmetric AES(encryptionKey) over agentKey + requestId — a different scheme from the outbound HMAC. Both live in DokuPayoutServiceProperties.
// Inbound Doku webhook (unpaid / refund): re-compute AES(agentKey + requestId)
// with the configured encryption key and compare.
override fun verifySignature(agentKey: String, requestId: String, signature: String): Boolean {
    if (agentKey != properties.agentKey)
        throw IllegalStateException("Invalid agentKey: $agentKey")

    val localSignature = encrypt(agentKey + requestId, properties.encryptionKey)
    if (localSignature != signature)
        throw IllegalStateException("Invalid signature not match: $localSignature != $signature")
    return true
}

private fun encrypt(plainString: String, encryptionKey: String): String {
    val key     = SecretKeySpec(encryptionKey.toByteArray(), "AES")
    val cipher  = Cipher.getInstance("AES")
    cipher.init(Cipher.ENCRYPT_MODE, key)
    return Base64.getEncoder().encodeToString(cipher.doFinal(plainString.toByteArray()))
}

// Top-up notification (Rintis shown; Artajasa is identical) → wallet credit
// happens on ANOTHER service via a child workflow on its task queue.
private fun startCreditTopupWalletWorkflow(order: RintisTransactionOrder) {

        TopupWalletWorkflow::class.java,
        ChildWorkflowOptions.newBuilder()

            .setTaskQueue(TemporalConfig.ACCOUNT_SERVICE_TASK_QUEUE)  // account-service worker

            .build()
    )

        order.accountNumber, order.amount,
        order.partnerTransactionId, order.referenceNumber
    )
}
