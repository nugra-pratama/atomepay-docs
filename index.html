AtomePay (APB) — Platform Documentation

AtomePay is Atome's Indonesia digital-wallet & pay-later backend platform. This site documents the microservices, REST APIs, Temporal workflows, provider integrations, and infrastructure under the atomepay GitHub org.

Source of truth
Code is the source of truth. All ~30 org repos are cloned locally; each service is self-contained. Endpoint lists here are an inventory to locate code, not a substitute for reading the controllers.

System architecture

APB is a set of independently deployable Spring Boot 3 microservices (Kotlin, Java 21) orchestrated with Temporal for every multi-step / external-dependent flow. PostgreSQL (JPA/Hibernate, Flyway) holds transactional state, MongoDB holds reference data, Redis holds cache/transient state, Kafka handles messaging, and Spring Cloud Config centralizes configuration.

APB system overview — gateway fronting, Temporal-orchestrated microservices, and provider adapters (Doku / GDC / Artajasa / Rintis / Atome).

  • API gateway fronts public consumer endpoints; each service is also independently reachable internally.
  • Temporal runs workflows + activities (e.g. AtomeTransferWorkflow, DokuTransferWorkflow, GdcTransferWorkflow, *RecordBookingWorkflow).
  • Provider adapters: Doku (PPOB billers, cashout, payouts), GDC Pay (bank transfer), Artajasa (QRIS, top-up), Rintis (top-up notifications), Atome (internal wallet transfer).
  • Observability: Spring Actuator + Prometheus + Logstash JSON logs.
Temporal queues
Shared queues: ACCOUNT_SERVICE_TASK_QUEUE, TOPUP_RECORD_BOOKING_TASK_QUEUE, TRANSFER_RECORD_BOOKING_TASK_QUEUE, QRIS_RECORD_BOOKING_TASK_QUEUE, PPOB_TASK_QUEUE, TRANSACTION_HISTORY_SERVICE_TASK_QUEUE.

Security model

  • Public / partner-facing API → JWT resource server (JWTAuthenticationFilter), issuer OAUTH2_JWT_ISSUER_URI.
  • Internal service-to-service → shared API key ZERO_TRUST_SERVICE_KEY via InternalApiFilter (e.g. RintisApiFilter in account-service is a variant).
  • Back-office → BackofficeApiFilter; Client token → ClientTokenAuthenticationFilter.

Transfer flows

All confirm endpoints share a shape: validate JWT/booking → start a Temporal workflow (async) → booking marked PROCESSED → respond immediately with the booking reference. A *RecordBookingWorkflow tracks the booking lifecycle; a final confirmBooking signal (in finally) completes it, otherwise the booking expires (~15 min).

Atome — internal wallet transfer (no saga)

sequenceDiagram autonumber participant C as Client participant T as transfer-service participant W as WalletTransferWorkflow (child) participant H as transaction-history-service participant N as notification-service C->>T: POST /api/v1/transfers/atome/confirm T->>T: validate JWT / booking / amount range T->>T: start AtomeTransferWorkflow (Temporal) Note over T: booking status = PROCESSED, respond with reference T->>T: create AtomeTransactionOrder (RECEIVED) T->>H: record outbound history PENDING (async) T->>W: start WalletTransferWorkflow W->>W: debit source / credit recipient (atomic) W-->>T: done alt success T->>T: order -> PROCESSED_SUCCESS / WALLET_SEND -> COMPLETED T->>N: push to sender (always) T->>H: WALLET_RECEIVE COMPLETED T->>N: push to recipient (success only) else failure T->>T: order -> PROCESSED_FAILED / WALLET_SEND -> FAILED end T->>T: signal confirmBooking (finally)

Atome internal wallet transfer — no saga, no external payout. Atomicity lives inside the wallet child workflow.

Amount-range check ([minimumAmount, maximumAmount] from booking) is Atome-specific. No saga compensation — atomicity is inside the wallet child workflow.

Doku — bank transfer, transactional saga + async webhooks

sequenceDiagram autonumber participant C as Client participant T as transfer-service participant D as Doku participant W as BankTransferDebitWorkflow (child) participant E as ekyc-service participant N as notification-service C->>T: POST /api/v1/transfers/doku/confirm T->>E: fetch KYC status (verified / unverified) T->>W: start BankTransferDebitWorkflow -> HOLD balance T->>D: POST /payout D-->>T: response T->>T: create DokuTransactionOrder (RECEIVED) / history PENDING alt status InProgress / Timeout / Unknown T->>D: poll Doku status D-->>T: status end alt final SUCCESS / FAILED T-->>W: commit / release hold T->>N: push notification T->>T: record final history else still RECEIVED Note over T: no history, no wallet finalize - exit, await async webhook D->>T: POST /notifications/unpaid (or /refund) T->>T: verify AES + agentKey signature / find order by transactionId T->>T: DokuNotificationWorkflow -> commit/release hold T->>N: push notification else error Note over T: SAGA COMPENSATION T->>T: order -> FAILED / release wallet hold end T->>T: signal confirmBooking (finally)

Doku bank transfer — transactional saga with hold, polling, async webhook finalization, and saga compensation on error.

Async path: Doku → POST /api/v1/transfers/doku/notifications/unpaid (or /refund) → verify AES+agentKey signature → DokuNotificationWorkflow → BankTransferConfirmDebitWorkflow (commit/release), final history, push notification.

GDC — bank transfer, saga + signal/timeout wait

sequenceDiagram autonumber participant C as Client participant T as transfer-service participant G as GDC participant W as BankTransferDebitWorkflow (child) participant N as notification-service C->>T: POST /api/v1/transfers/gdc/confirm T->>W: start BankTransferDebitWorkflow -> HOLD balance T->>G: POST /payout G-->>T: response T->>T: create GdcTransactionOrder (RECEIVED) / history PENDING par signal vs timeout G->>T: webhook -> signal cancelCheckStatusDelay T->>T: re-fetch refreshed order and Note over T: timeout (N min) -> GDC status check activity T->>G: status check G-->>T: status -> order PROCESSED_SUCCESS / FAILED end T-->>W: commit / release hold T->>N: push notification T->>T: record final history (COMPLETED / FAILED / PENDING) Note over T: on error -> saga compensation: order FAILED + release hold T->>T: signal confirmBooking (finally)

GDC bank transfer — the webhook signals the waiting workflow to unblock, avoiding the timeout wait.

GDC settles via a webhook that unblocks the waiting workflow (avoids timeout wait).

Transfer routing (inquiry → provider)

POST /api/v1/transfers/inquiry → TransferRoutingService.determineGateway(): (1) smart rules (preferred bank-code exact match, then preferred amount threshold), (2) weighted percentage split (weights must sum to exactly 100). Forward via RequestDispatcher to /api/v1/transfers/{partner}/inquiry, then cache transfer:{bookingId} → partnerName in Redis (TTL 15 min). Config atomepay.partners.routing.transfer is @RefreshScope hot-reloadable from Config Server.

QRIS · Top-up · PPOB

  • QRIS (payment-service + account-service): Artajasa QRIS payment/refund, network sign-on/sign-off/echo/cutover; QRIS payload parsing via QrisParser in atomepay-common. Routes under /api/v1/qr, /api/v1/qr/artajasa.
  • Top-up (topup-service): Artajasa top-up + status inquiry (POST /status-inquiry); Rintis notification ingestion under /api/v1/rintis/notification.
  • PPOB (ppob-service): biller inquiry + payment via Doku; routes under /api/v1/biller/doku, orders under /api/v1/biller.

e-KYC

ekyc-service exposes /api/v1/kyc (request, consent, KTP-image, liveness-check, personal-data, workflows), /api/v1/backoffice/kyc and /api/v1/internal/kyc. Workflow: request → consent → KTP image → OCR → liveness → fraud assessment. Encryption: AES-GCM with Aliyun KMS.

Local development

# Build one service (also builds shared/atomepay-common)
cd /opt/atomepay/<service> && ./mvnw clean install

# List endpoints in a service
grep -rhoE '@(Get|Post|Put|Patch|Delete|Request)Mapping\("([^"]+)"\)' src/main | sort -u

# Read transfer flow diagrams (richest docs in the org)
cat transfer-service/docs/{general,atome,doku,gdc}-transfer-flow.md

# git safety for cloned repos (dubious ownership)
git -c safe.directory=/opt/atomepay/<repo> log --oneline -1
Staging DB access
Use atomecli saturn mysql/redis/mongo/es for staging lookups only (s6_* = ID AFI, s5_my = MY). Always confirm before writes.
